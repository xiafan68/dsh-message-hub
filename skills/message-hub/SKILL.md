# Message Hub 操作指南

> 面板是给人看的，`hub_*` 工具是给你用的。默认顺序：**先探活，再看数据，最后动手**。

这份文档只讲「怎么用这套工具把事办成」。接口细节在工具 description 里，这里讲组合与边界。

## 何时用（以及何时不用）

用：用户问订阅源/条目/精选；要加、停、删、立刻采集；要收藏；说「这条」「刚才那个源」但没指明。

不用：用户只是给你一个 URL 让你读（那是网页抓取，不用 `hub_*`）；用户问的是别的阅读器或别的系统的订阅。

## 工具地图

| 想要 | 调用 | 写 |
|---|---|---|
| 引擎是否在线、源/条目总数、最近采集 | `hub_status` | |
| 拉起没在跑的引擎 | `hub_service_start` | ✓ |
| 源列表（状态 / 条目数 / 上次采集） | `hub_feeds` | |
| 条目流（关键词 / 来源 / 日期 / 收藏 / 分页） | `hub_items` | |
| 单条正文摘要 + 链接 | `hub_item` | |
| 收藏 / 取消收藏 | `hub_item(action=like/unlike)` | ✓ |
| 每日 / 每周精选 | `hub_digest` | |
| 用户此刻在面板里选中的东西 | `hub_selection` | |
| 加源 | `hub_feed_add` | ✓ |
| 启停 / 删除 / 立刻采集 | `hub_feed_control` | ✓ |
| 关注方向（精选的取舍口径） | `hub_preferences` | ✓ |

## 流程 A：先看现状（大多数问题的第一步）

1. `hub_status` —— 在线吗？多少源、多少条？最近一次采集是什么时候？
2. 不在线 → `hub_service_start`，并告诉用户「首次启动会装依赖，可能需要几分钟」；起来后再 `hub_status` 一次。
3. 在线 → `hub_feeds`，用 `q` / `status` 收窄（例如只看 `status=error` 找坏源）。

不要跳过第 1 步直接 `hub_items`：引擎不可达时每个工具都会返回同一段"服务没在跑"，白费一轮。

## 流程 B：读条目

1. `hub_items`：带 `q`（标题/摘要关键词）、`source_id`、`liked`、`from_date` / `to_date`、`limit`。返回里每条有 `#id`、来源、时间、摘要。
2. 用户要正文 → `hub_item(id)`。只有这一条会返回较长摘要（截断到 1200 字），别对列表里的每条都调。
3. 需要更多上下文就翻页（`offset`），不要重复同一个查询。

`hub_item` 只在**最近 100 条**里按 id 找。找不到就明说，并用 `hub_items` + 关键词/日期重新定位——**不要编造条目内容**。

## 流程 C：精选

- 不传 `collection_id`：列出各期（`kind=daily|weekly`），每期带标题、区间与摘要。
- 展开某一期：**带 `collection_id` 再调一次**（列表里的 `id`）。
- 展开后优先讲 `rationale`（入选理由）—— 这是精选相对普通列表的全部价值；引用时把理由一起带上。
- 返回「还没有精选取集」：说明精选由引擎之外的脚本生成，**不等于「最近没有新闻」**，别这样告诉用户。

## 流程 D：加源

三种类型，参数不同：

| type | 必填 | 说明 |
|---|---|---|
| `rss` | `url` | 也覆盖 Atom；给的是 feed 地址，不是站点首页 |
| `github_releases` | `repository` | `owner/name`，内部会拼 `releases.atom` |
| `web_page` | `config` 完整对象 | 需要 request / extract / detect；一句话塞不进 CSS 选择器 |

- 用户没说清 feed 地址时**先问**，不要猜站点首页当 feed（十有八九解析失败）。
- `id` 用英文/数字/连字符；不传会按名称生成，可能不好记，重要源建议显式给。
- 加完**不会立刻抓取**。问一句「要不要现在抓一次」，得到同意再 `hub_feed_control(action="run")`——它会真发网络请求，十几秒很正常。
- `web_page` 缺 `config` 就明说加不了，并解释需要哪些字段；不要用示例值糊一个。

## 流程 E：维护

- 暂停/恢复：`hub_feed_control(action=disable|enable)`；删除是软删，提醒用户历史条目仍在。
- 坏源排查：`hub_feeds(status="error")` → 看 `last_run_at` → 先 `run` 一次看新错误，再决定停用还是删。
- 收藏：`hub_item(action=like)`；收藏的条目不会被两周清理带走。
- 关注方向：这些词是精选的取舍口径。`add` / `remove` 用**精确文本**匹配（用户自己的措辞），不要模糊替换同义词；`set` 是整份覆盖。

## 面板联动（`hub_selection`）

- 用户在面板里选中条目或源，会自动上报；`hub_selection` 读到的就是它。
- 用户说「这条」「这个 feed」「刚才看的那个」→ **先调 `hub_selection`**，再决定展开还是回答；读不到就问用户要哪条。
- 选中是**快照**：按会话隔离，6 小时过期，插件重启即丢；也可能比 `hub_items` 的结果旧。以工具返回为准，别假设"面板里现在的"。
- 面板的「写进对话草稿」只写草稿、不自动发送；用户可以接着补问题。

## 硬约束

1. **不编条目**：任何 `#id`、标题、链接、时间必须来自工具返回；没有就说没有。
2. **不假装采集**：`run` 真的会发请求；失败照实转述 `error`，别总结成"已更新"。
3. **不跳过探活**：`hub_status` 是第一步，也是失败时的归因依据。
4. **摘要够用就别拉正文**：一次列表 + 一两条详情，通常就够回答。
5. **说人话**：中文回答（用户用英文才用英文），条目按「来源 · 标题 · 时间」组织，链接放后面。

## 失败处置

| 返回 | 含义 | 动作 |
|---|---|---|
| 「服务没在跑」/ `service-down` | 引擎没起 | `hub_service_start`；仍失败就让用户看 `runtimeDir` 下的 `service.log` / `install.log` |
| 401 / 403 | token 缺失或不一致 | 说明是鉴权问题，让用户检查 `config.token` / `tokenFile` |
| 「没有匹配的条目」 | 真的没有 | 放宽日期或关键词再试一次；不要用别的来源凑 |
| 「在最近 100 条里没找到」 | 条目太旧 | 用 `hub_items` + 日期区间重新定位 |
| 「不支持的 type」 | 类型写错 | 只有 `rss` / `github_releases` / `web_page` |
| 「web_page 需要 config」 | 参数不全 | 明说需要 request/extract/detect，不要硬编 |

## 三段示例

**「我订了哪些源？有没有挂的？」**
→ `hub_status`（在线、源数、条目数）→ `hub_feeds(status="error")` → 汇总：共 N 个源，X 正常、Y 需处理；逐个给 id / 名称 / 上次采集时间，最后问要不要对坏源 `run` 或先 `disable`。

**「今天的精选讲了什么？」**
→ `hub_digest(kind="daily", limit=3)` → 取最新一期的 `id` → `hub_digest(collection_id=...)` → 按 3–5 条讲，每条带**入选理由**和链接，最后问要不要展开某条原文（`hub_item`）。

**「帮我订 Simon Willison 的博客」**
→ 没有 feed 地址就问（不要猜 `/blog` 首页）→ 拿到后 `hub_feed_add(kind="rss", url=..., name="Simon Willison")` → 报告新建的 id 与类型 → 问是否立刻 `run` 一次。
